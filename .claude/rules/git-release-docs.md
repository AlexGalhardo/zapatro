# Git, release, CI e documentação

- **Docs sempre atualizados:** toda mudança de código atualiza, no mesmo lote, `PLAN.md` (checklist `[ ]`/`[x]`/`[~]`), `CHANGELOG.md` (`[Unreleased]`) e o doc afetado em `docs/`. Fluxo repetitivo ou armadilha descoberta → criar/atualizar uma skill em `.claude/skills/`.
- **Conventional Commits 1.0.0** (com escopo: `feat(ui): …`, o escopo vira o prefixo da nota do release) e **SemVer 2.0.0**. Micro-commits, **sem bump nem tag por commit**: as mudanças entram em `[Unreleased]` no CHANGELOG. **Releases são poucos e em ordem** (11 até 2026-10-25: `v0.1.0` a `v0.10.0` no repo privado antigo e `v0.11.0`, o primeiro no `zeta-c`; depois patch `0.11.1` para correção pequena e minor `0.12.0` para o próximo passo); só o dev decide quando sai o próximo: junte `[Unreleased]` numa seção `## [versão] - data`, suba o `package.json`, tag anotada `v<versão>`, `bun run graph`, push e `bun run release` (notas = a seção). **Todo release gera o `.exe` portátil do Windows na raiz do projeto** (`Zapatro-<versão>-win-x64.exe`, gitignored, `bun run exe`) para o dev testar, e o anexa ao GitHub Release. **Push e release só quando o usuário pedir explicitamente.** Skill `release-section`.
- **Hooks** em `.githooks/` (`commit-msg`: Conventional Commits; `pre-commit`: Biome, `bun check` e markdownlint); ligados pelo `bun install` (`core.hooksPath`). **Gates à mão:** `bun run check`, `bun run lint:md`, `bun run typecheck`, `bun test`; `bun run build` antes de push. Nunca `--no-verify`.
- **Graphify antes de todo push** para a `main`: `bun run graph` (o grafo em `graphify-out/` é gitignored e fica local).
- **QA:** `bun scripts/smoke.ts` sempre; `bun scripts/qa.ts` (skill `qa-global`) a partir do PRÉ-ALPHA; checklist em `docs/quality-assurance-functional-systems-global-test.md`. Testes curtos: nunca soak/QA de horas.
- **CI/CD** (`.github/workflows/`):
  - `ci.yml` (push/PR na `main`): format, lint, `bun check`, testes, smoke Playwright no build de produção, **Electron** empacotado + smoke (Linux, Windows e macOS) e **APK Android** de debug.
  - `deploy.yml` (push em `main`): `site:build` e deploy do site na Vercel, projeto `beta.lekzera.xyz` (<https://beta.lekzera.xyz>); secrets `VERCEL_TOKEN`, `VERCEL_ORG_ID`, `VERCEL_PROJECT_ID`. O site de produção `truco.lekzera.xyz` segue no `site:deploy` à mão.
  - `release.yml` (tag `v*`): zips web (completo, demo e Poki), zips Electron por SO, AAB/APK Android (assinados se houver os secrets `ANDROID_KEYSTORE_*`), checksums e GitHub Release com as notas do CHANGELOG.
  - O release sai da máquina local (`bun run release`, `scripts/release.ts`): no repo privado antigo o Actions costumava ficar sem minutos; no `zeta-c`, público, os minutos são livres. Quando o `release.yml` roda, ele só anexa ao release existente o que falta (macOS, AAB assinado).
- **Remoto único:** `origin` → `https://github.com/AlexGalhardo/zeta-c.git` (**público**, histórico novo desde 2026-10-25; o repo privado antigo `AlexGalhardo/truco.lekzera.xyz` guarda o histórico anterior; branch única `main`, sem `dev` desde 2026-10-25; `pixel-art` = a linha em pixel art até `v1.0.0-rc.51`, congelada). O Gridbound (template de origem) vive em `AlexGalhardo/tibia-roguelite-game`: não use nada de lá sem pedido.
- **Worktrees** (PLAN §12.1): as antigas `../jogo-truco-assets` (`assets`) e `../jogo-truco-qa` (`qa`) foram encerradas e integradas (2026-10-25). Worktree nova só com pedido; cada uma edita só os arquivos de que é dona e o fio principal integra com merge na `main` depois dos gates.
- **Site** (<https://truco.lekzera.xyz>, `docs/site.md`): `/play/` = jogo completo, `/demo/` = demo (até o primeiro chefe). Republique (`site:build` + `site:deploy`) quando a mudança chegar ao jogador web; trailer e presskit só com pedido do usuário.
